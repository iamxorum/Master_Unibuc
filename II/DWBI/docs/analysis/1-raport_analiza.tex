\label{sec:descriere}

\section{Modelul de date ales}

TickLy este un sistem de management al tichetelor de suport care permite gestionarea a cererilor de asistență de la clienți. Modelul de date ales este un \textbf{model entitate-relație} extins care suportă atât clienți persoane fizice, cât și juridice, cu un sistem flexibil de categorisire și urmărire a tichetelor.

Sistemul este organizat în două straturi principale:
\begin{itemize}
    \item \textbf{Baza de date OLTP} - pentru operațiunile transacționale zilnice (creare tichete, comentarii, asignări agenți)
    \item \textbf{Data Warehouse} - pentru analize și raportare (model stea pentru analize multidimensionale)
\end{itemize}

\section{Obiectivele Aplicației}

Obiectivele principale ale aplicației TickLy sunt:

\begin{enumerate}
    \item \textbf{Gestionarea a tichetelor de suport} - urmărirea completă a ciclului de viață al tichetelor de la creare până la rezolvare
    \item \textbf{Analiza performanțelor agenților} - monitorizarea timpului de rezolvare, numărul de tichete rezolvate, rating-urile primite
    \item \textbf{Analiza satisfacției clienților} - urmărirea feedback-ului și identificarea tendințelor
    \item \textbf{Optimizare} - analiza distribuției tichetelor pe departamente și agenți
    \item \textbf{Identificarea problemelor recurente} - analiza categoriilor și subiectelor pentru a identifica problemele cele mai frecvente
    \item \textbf{Raportare} - generarea de rapoarte pentru management
\end{enumerate}

Baza de date OLTP conține următoarele: 

\subsubsection{Entități independente}

\begin{enumerate}
    \item \textbf{CLIENT} — entitate părinte pentru clienți
    \item \textbf{AGENT} — agenții de suport
    \item \textbf{PRIORITATE} — nivelurile de prioritate ale tichetelor
    \item \textbf{STATUS} — statusurile tichetelor
    \item \textbf{TOPIC} — entitate părinte pentru topic-urile asociate tichetelor
    \item \textbf{CATEGORIE} — categoriile pentru organizarea tichetelor
    \item \textbf{TAG} — tag-uri pentru etichetarea tichetelor
    \item \textbf{DEPARTAMENT} — departamentele organizației
\end{enumerate}

\textbf{Nota:} Categorie este o entitate de referinta catre categoria parinte.

\subsubsection{Entități dependente}

\begin{enumerate}
    \item \textbf{TICKET} — tichetele de suport
    \item \textbf{ATASAMENT} — atașamentele la tichete
    \item \textbf{KB\_ARTICLE} — documentație
    \item \textbf{FEEDBACK} — feedback-urile la tichete
    \item \textbf{SOLUTIE} — soluțiile la tichete
    \item \textbf{ADRESA} — adresele clientilor
\end{enumerate}

\subsubsection{Entități de tip IS-A}

\begin{enumerate}
    \item \textbf{CLIENT $\rightarrow$ CLIENT\_FIZICA / CLIENT\_JURIDICA} — clienți persoane fizice sau juridice
    \item \textbf{TOPIC $\rightarrow$ TOPIC\_SERVICIU / TOPIC\_PRODUS} — topic-uri de tip serviciu sau produs
\end{enumerate}

\subsubsection{Relații Many-to-Many}

Sistemul conține următoarele relații many-to-many (M:N), implementate prin tabele asociative:

\begin{itemize}
    \item \textbf{Ticket $\leftrightarrow$ Agent} (prin \texttt{TICKET\_AGENT}) - un ticket poate fi asignat mai multor agenți, iar un agent poate lucra la mai multe tichete
    \item \textbf{Ticket $\leftrightarrow$ Topic} (prin \texttt{TICKET\_TOPIC}) - un ticket poate fi asociat cu mai multe topic-uri, iar un topic poate fi asociat cu mai multe tichete
    \item \textbf{Agent $\leftrightarrow$ Departament} (prin \texttt{AGENT\_DEPARTAMENT}) - un agent poate aparține mai multor departamente, iar un departament poate avea mai mulți agenți
    \item \textbf{Ticket $\leftrightarrow$ Tag} (prin \texttt{TICKET\_TAG}) - un ticket poate avea mai multe tag-uri, iar un tag poate fi asociat cu mai multe tichete
    \item \textbf{Ticket $\leftrightarrow$ Client} (prin \texttt{COMMENT\_CLIENT}) - un ticket poate avea mai multe comentarii de la client, iar un client poate avea mai multe comentarii la tichete
    \item \textbf{Ticket $\leftrightarrow$ Agent} (prin \texttt{COMMENT\_AGENT}) - un ticket poate avea mai multe comentarii de la agent, iar un agent poate avea mai multe comentarii la tichete
\end{itemize}

\section{Structura Modelului Stea}

Modelul stea implementat pentru TickLy conține:

\subsubsection{Tabel de Fapte}

\begin{itemize}
    \item \textbf{FACT\_TICKET} - tabelul central de fapte care stochează măsurile și metricile asociate tichetelor
\end{itemize}

\subsubsection{Tabele Dimensiune}

\begin{enumerate}
    \item \textbf{DIM\_CLIENT} - dimensiunea clienților (Type 2 SCD pentru istoricizare)
    \item \textbf{DIM\_AGENT} - dimensiunea agenților (Type 2 SCD)
    \item \textbf{DIM\_DEPARTAMENT} - dimensiunea departamentelor (Type 2 SCD)
    \item \textbf{DIM\_CATEGORIE} - dimensiunea categoriilor (Type 1 SCD)
    \item \textbf{DIM\_TOPIC} - dimensiunea topic-urilor (Type 1 SCD)
    \item \textbf{DIM\_TAG} - dimensiunea tag-urilor (Type 1 SCD)
    \item \textbf{DIM\_TIME} - dimensiunea temporală pentru analize pe perioade
\end{enumerate}

\begin{itemize}
    \item \textbf{Nota - Type 1 SCD:} nu permite urmărirea istoricului modificărilor.
    \item \textbf{Nota - Type 2 SCD:} permite urmărirea istoricului modificărilor.
\end{itemize}

\section{Caracteristici ale Modelului}

\begin{itemize}
    \item \textbf{Slowly Changing Dimensions (SCD)}: Dimensiunile \texttt{DIM\_CLIENT}, \texttt{DIM\_AGENT} și \texttt{DIM\_DEPARTAMENT} sunt implementate ca Type 2 SCD, permițând urmărirea istoricului modificărilor
    \item \textbf{Degenerări}: Status și Prioritate sunt degenerate în tabelul de fapte (stocate direct în \texttt{FACT\_TICKET})
    \item \textbf{Dimensiune Conformată}: Dimensiunea temporală \texttt{DIM\_TIME}
\end{itemize}

\chapter{Partiționarea Tabelelor}
\label{sec:partitii}

\section{Tabelul FACT\_TICKET - Partiționare pe Range (Date)}

\subsubsection{Justificare}

Tabelul \texttt{FACT\_TICKET} va crește continuu în timp, devenind foarte mare. Partiționarea pe baza datei de creare a ticketului (\texttt{date\_creare\_key}) oferă următoarele avantaje:

\begin{itemize}
    \item \textbf{Query Performance}: Cererile care filtrează pe perioade specifice vor accesa doar partițiile relevante (partition pruning)
    \item \textbf{Maintenance}: Părțile vechi ale datelor pot fi arhivate sau șterse ușor (drop partition)
    \item \textbf{Parallel Operations}: Operațiile de indexare și întreținere pot rula în paralel pe diferite partiții
    \item \textbf{Backup Selectiv}: Partițiile recente pot fi făcute backup mai frecvent decât cele vechi
\end{itemize}

\subsubsection{Strategie de Partiționare}

\textbf{Partiționare pe Range} pe \texttt{date\_creare\_key}:
\begin{itemize}
    \item \textbf{Partiție lunară}: Fiecare lună va avea o partiție separată
    \item \textbf{Partiție DEFAULT}: Pentru date viitoare sau date care nu se încadrează în intervalele definite
\end{itemize}

\textbf{Exemplu de partiții}:
\begin{itemize}
    \item \texttt{P\_2024\_01}: Ianuarie 2024 (date\_key: 20240101 - 20240131)
    \item \texttt{P\_2024\_02}: Februarie 2024 (date\_key: 20240201 - 20240229)
    \item \texttt{P\_2024\_03}: Martie 2024 (date\_key: 20240301 - 20240331)
    \item \ldots
    \item \texttt{P\_DEFAULT}: Toate celelalte date
\end{itemize}

\subsubsection{Cerere în Limbaj Natural}

\textbf{Cerere}: "Să se calculeze numărul total de tichete create în fiecare lună din anul 2024, grupate pe departamente, pentru tichetele cu prioritate ridicată (nivel 4 sau 5) care au fost rezolvate în mai puțin de 24 de ore."

Această cerere va beneficia de partiționare prin:
\begin{itemize}
    \item \textbf{Partition Pruning}: Oracle va accesa doar partițiile pentru lunile din 2024, ignorând toate celelalte partiții
    \item \textbf{Index Efficiency}: Indecșii locali pe fiecare partiție vor fi mai mici și mai eficienți
    \item \textbf{Parallel Execution}: Dacă cererea necesită scanarea mai multor partiții, Oracle poate procesa partițiile în paralel
\end{itemize}

\section{Tabelul DIM\_CLIENT - Partiționare pe Hash (client\_key)}

\subsubsection{Justificare}

Dimensiunea \texttt{DIM\_CLIENT} este o dimensiune Type 2 SCD care poate crește semnificativ datorită istoricizării. Partiționarea pe hash pe \texttt{client\_key} oferă:

\begin{itemize}
    \item \textbf{Distribuție Uniformă}: Datele sunt distribuite uniform pe partiții, evitând partiții "hot"
    \item \textbf{Join Performance}: Join-urile cu \texttt{FACT\_TICKET} pot beneficia de partition-wise joins dacă și fact table este partiționat corespunzător
    \item \textbf{Load Balancing}: Operațiile ETL vor fi distribuite uniform pe partiții
\end{itemize}

\subsubsection{Strategie de Partiționare}

\textbf{Partiționare pe Hash} pe \texttt{client\_key}:
\begin{itemize}
    \item \textbf{Număr de partiții}: 8 sau 16 (în funcție de volumul de date)
    \item Fiecare partiție va conține aproximativ același număr de înregistrări
\end{itemize}

\subsubsection{Cerere în Limbaj Natural}

\textbf{Cerere}: "Să se identifice toți clienții care au creat mai mult de 10 tichete în ultimele 6 luni și care au un rating mediu mai mic de 3 stele, afișând detalii despre tipul de client și departamentele cu care au interacționat cel mai des."

Această cerere va beneficia de partiționare prin:
\begin{itemize}
    \item \textbf{Parallel Scans}: Oracle poate scana toate partițiile în paralel pentru a identifica clienții care îndeplinesc criteriile
    \item \textbf{Reduced Contention}: Operațiile pe diferite partiții nu se blochează reciproc
    \item \textbf{Efficient Aggregation}: Agregările pe partiții pot rula în paralel
\end{itemize}

\section{Formularea Cererii în Limbaj Natural}

    \item Numărul de tichete cu prioritate ridicată (nivel 4 sau 5)
    \item Procentul de tichete rezolvate în timpul standard (conform prioritate)
    \item Top 3 agenți cu cele mai multe tichete rezolvate
\end{itemize}

Rezultatele trebuie să fie filtrate doar pentru departamentele cu cel puțin 100 de tichete în perioada analizată și să fie sortate descrescător după numărul total de tichete."

\section{Tehnici de Optimizare}

\subsubsection{1. Materialized View cu Query Rewrite}

\textbf{Avantaje}:
\begin{itemize}
    \item Rezultatele pre-calculate reduc timpul de execuție de la minute la secunde
    \item Query rewrite automat - Oracle folosește MV-ul fără modificarea cererii
    \item Refresh incremental posibil pentru actualizări eficiente
\end{itemize}

\textbf{Dezavantaje}:
\begin{itemize}
    \item Spațiu suplimentar de stocare
    \item Necesită proces de refresh (complet sau incremental)
    \item Datele pot fi ușor învechite între refresh-uri
\end{itemize}

\textbf{Recomandare}: Utilizare pentru rapoarte periodice (zilnice/săptămânale) unde ușoara învechire a datelor este acceptabilă.

\subsubsection{2. Indecși Compuși pe Fact Table}

Crearea de indecși compuși pe \texttt{FACT\_TICKET}:
\begin{itemize}
    \item \texttt{(date\_creare\_key, departament\_key, status\_este\_final)}
    \item \texttt{(departament\_key, prioritate\_nivel, status\_este\_final)}
\end{itemize}

\textbf{Avantaje}:
\begin{itemize}
    \item Acces rapid la datele filtrate
    \item Reducerea I/O-ului pentru operații de filtrare și agregare
    \item Suport pentru operații de sortare eficiente
\end{itemize}

\textbf{Dezavantaje}:
\begin{itemize}
    \item Spațiu suplimentar pentru indecși
    \item Overhead la inserare/actualizare (indecșii trebuie menținuți)
    \item Risc de creștere excesivă dacă se creează prea mulți indecși
\end{itemize}

\textbf{Recomandare}: Utilizare pentru coloane frecvent folosite în WHERE și GROUP BY.

\subsubsection{3. Partition Pruning}

Cu partiționarea pe \texttt{date\_creare\_key}, Oracle va accesa doar partițiile relevante pentru ultimii 2 ani.

\textbf{Avantaje}:
\begin{itemize}
    \item Reducere dramatică a I/O-ului (doar partițiile relevante sunt scanate)
    \item Timp de execuție redus proporțional cu numărul de partiții eliminate
    \item Eficiență crescută pentru analize pe perioade specifice
\end{itemize}

\textbf{Dezavantaje}:
\begin{itemize}
    \item Necesită partiționare corectă a tabelelor
    \item Overhead de management al partițiilor
    \item Potențial de partiții neuniforme dacă distribuția datelor este inegală
\end{itemize}

\textbf{Recomandare}: Utilizare obligatorie pentru tabele mari cu filtrare temporală frecventă.

\subsubsection{4. Bitmap Join Indexes}

Crearea de bitmap join indexes între \texttt{FACT\_TICKET} și dimensiuni:
\begin{itemize}
    \item \texttt{FACT\_TICKET.departament\_key} JOIN \texttt{DIM\_DEPARTAMENT.departament\_key}
    \item \texttt{FACT\_TICKET.date\_creare\_key} JOIN \texttt{DIM\_TIME.date\_key}
\end{itemize}

\textbf{Avantaje}:
\begin{itemize}
    \item Eliminarea join-urilor costisitoare pentru filtrare
    \item Operații logice pe biți foarte rapide
    \item Eficiență pentru agregări pe dimensiuni
\end{itemize}

\textbf{Dezavantaje}:
\begin{itemize}
    \item Overhead semnificativ la inserare/actualizare
    \item Necesită mentenanță atentă
    \item Potențial de blocare în medii OLTP (dar acceptabil în DW)
\end{itemize}

\textbf{Recomandare}: Utilizare pentru dimensiuni stabile cu cardinalitate redusă și filtrare frecventă.

\subsubsection{5. Parallel Query Execution}

Folosirea paralelismului pentru procesarea cererii.

\textbf{Avantaje}:
\begin{itemize}
    \item Utilizare eficientă a resurselor multi-core
    \item Reducere a timpului de execuție proporțional cu numărul de procesoare
    \item Scalabilitate pentru volume mari de date
\end{itemize}

\textbf{Dezavantaje}:
\begin{itemize}
    \item Consum crescut de CPU și memorie
    \item Potențial de degradare a performanței altor cereri simultane
    \item Necesită configurare atentă a parametrilor de paralelism
\end{itemize}

\textbf{Recomandare}: Utilizare pentru cereri complexe pe volume mari de date, în timpuri de utilizare redusă sau pe servere dedicate.

\section{Strategie Recomandată de Optimizare}

Pentru cererea specificată, recomandăm următoarea combinație:

\begin{enumerate}
    \item \textbf{Partiționare pe Range} pe \texttt{date\_creare\_key} (obligatoriu) - pentru partition pruning
    \item \textbf{Materialized View} cu refresh zilnic - pentru rapoarte periodice
    \item \textbf{Indecși compuși} pe coloanele frecvent filtrate - pentru cereri ad-hoc
    \item \textbf{Bitmap indexes} pe coloanele cu cardinalitate redusă - pentru filtrare rapidă
    \item \textbf{Parallel execution} cu grad moderat (4-8) - pentru procesare eficientă
\end{enumerate}

\section{Cerere Simplă (Nivel 1)}

\textbf{Descriere}: "Să se afișeze numărul total de tichete create în fiecare lună din anul 2024."

\textbf{Complexitate}: Scăzută - o singură agregare temporală, fără join-uri complexe.

\textbf{Raport propus}: Grafic de tip bar chart sau line chart cu lunile pe axa X și numărul de tichete pe axa Y.

\section{Cerere Medie (Nivel 2)}

\textbf{Descriere}: "Să se calculeze timpul mediu de rezolvare al tichetelor, grupate pe departamente și pe niveluri de prioritate, pentru tichetele create în ultimul trimestru."

\textbf{Complexitate}: Medie - agregări pe multiple dimensiuni, filtrare temporală, join-uri cu dimensiuni.

\textbf{Raport propus}: Heatmap sau tabel pivot cu departamentele pe rânduri, prioritățile pe coloane și timpul mediu de rezolvare ca valoare.

\section{Cerere Medie-Avansată (Nivel 3)}

\textbf{Descriere}: "Să se identifice top 10 agenți cu cel mai bun rating mediu (minim 4.0) care au rezolvat cel puțin 50 de tichete în ultimele 3 luni, afișând pentru fiecare agent: numărul total de tichete rezolvate, rating-ul mediu, timpul mediu de rezolvare și departamentul din care face parte."

\textbf{Complexitate}: Medie-Avansată - filtrare complexă, agregări, sortare, top N, join-uri multiple.

\textbf{Raport propus}: Tabel sortabil cu top 10 agenți, cu posibilitatea de filtrare și export. Grafic de tip bar chart pentru compararea rating-urilor.

\section{Cerere Avansată (Nivel 4)}

\textbf{Descriere}: "Să se analizeze evoluția satisfacției clienților pe categorii de tichete, calculând pentru fiecare categorie și pentru fiecare trimestru din ultimul an: numărul de tichete, rating-ul mediu, procentul de tichete rezolvate în timpul standard și tendința de creștere/scădere a rating-ului comparativ cu trimestrul anterior."

\textbf{Complexitate}: Avansată - analiză temporală complexă, calcul de tendințe, agregări pe multiple niveluri, filtrare pe multiple criterii.

\textbf{Raport propus}: Dashboard cu multiple vizualizări:
\begin{itemize}
    \item Line chart pentru evoluția rating-ului pe trimestre
    \item Stacked bar chart pentru numărul de tichete pe categorii și trimestre
    \item Tabel cu metrici detaliate și indicatori de tendință (săgeți sus/jos)
    \item Gauge chart pentru procentul de tichete rezolvate în timpul standard
\end{itemize}

\section{Cerere Foarte Avansată (Nivel 5)}

\textbf{Descriere}: "Să se realizeze o analiză predictivă a volumului de tichete pentru următoarele 6 luni, pe baza tendințelor istorice, luând în considerare: sezonalitatea (lunile cu volum ridicat), tipul de client (persoană fizică vs. juridică), categoriile de tichete cu creștere accelerată și performanța departamentelor. Să se identifice și departamentele care ar putea necesita resurse suplimentare."

\textbf{Complexitate}: Foarte Avansată - analiză predictivă, calcul de tendințe complexe, analiză multi-dimensională, identificare de pattern-uri.

\textbf{Raport propus}: Dashboard executive cu:
\begin{itemize}
    \item Forecast chart (line chart cu predicții) pentru volumul de tichete
    \item Waterfall chart pentru factorii care influențează creșterea/scăderea
    \item Heatmap pentru identificarea categoriilor cu creștere accelerată
    \item Alert panel pentru departamentele care necesită atenție
    \item KPI cards pentru metrici cheie (volum estimat, resurse necesare)
\end{itemize}

\section{Cerere Complexă cu Drill-Down (Nivel 5)}

\textbf{Descriere}: "Să se creeze un raport interactiv care permite analiza performanțelor pe ierarhii: la nivel de an → trimestru → lună → săptămână, cu posibilitatea de filtrare pe departamente, agenți, tipuri de clienți și categorii. Raportul trebuie să afișeze: volumul de tichete, timpul mediu de rezolvare, rating-ul mediu, costul estimativ total și eficiența (tichete rezolvate / resurse alocate)."

\textbf{Complexitate}: Foarte Avansată - drill-down interactiv, analiză pe ierarhii, filtrare dinamică, calcul de eficiență, agregări pe multiple niveluri.

\textbf{Raport propus}: Dashboard interactiv OLAP-style cu:
\begin{itemize}
    \item Pivot table cu drill-down pe ierarhie temporală
    \item Filtre dinamice pentru toate dimensiunile
    \item Multiple chart-uri sincronizate (bar, line, pie)
    \item Export în Excel/PDF
    \item Funcționalitate de "drill-through" către detalii
\end{itemize}

\chapter{Concluzii}
\label{sec:concluzii}

Acest raport prezintă analiza completă a modelului de date pentru sistemul TickLy, acoperind toate aspectele cerute:

\begin{itemize}
    \item Modelul stea implementat oferă o structură optimă pentru analize multidimensionale
    \item Dimensiunile Type 2 SCD permit urmărirea istoricului modificărilor
    \item Indecșii bitmap și B-tree sunt optimizați pentru tipurile de cereri frecvente
    \item Partiționarea va îmbunătăți semnificativ performanța pentru analize temporale
    \item Cererile formulate acoperă un spectru larg de complexitate, de la rapoarte simple la analize predictive avansate
\end{itemize}

Implementarea acestor elemente va asigura o bază solidă pentru raportare și analiză de business în sistemul TickLy.
